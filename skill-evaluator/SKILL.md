# skill-evaluator Skill

Analyze `run-the-trace` JSON records to compute skill effectiveness metrics, and auto-pin/archive skills based on performance data.

## Problem this solves

- **`use_count` alone is misleading** — a skill could be used frequently but provide no actual benefit
- **Curator needs effectiveness data** — the curator at `~/.hermes/skills/.usage.json` tracks `use_count`, `view_count`, and `pinned` state, but has no data on whether a skill actually improves task outcomes
- **Skill pruning without insight** — auto-archiving skills based solely on usage frequency can remove skills that are valuable but used sparingly
- **Governance alignment** — in forensically_yours contexts, you need to know whether governance skills classify compliance accurately or just add latency

## What it does

When loaded, this skill:

1. **Reads all trace JSON files** from `~/.hermes/traces/` that were generated by `run-the-trace`
2. **Associates skill names with evaluations** by tracking which skill was active during each run (visible via `hermes skills list` during evaluation, or inferred from evaluation patterns if the user provides contextual identifiers in their task prompts)
3. **Computes effectiveness metrics** per skill:
   - `effective_rate` — percentage of evaluations where `skill_effective: true`
   - `avg_time_with_skill` — average execution time when skill was active
   - `avg_time_without_skill` — average execution time when skill was disabled
   - `tool_reduction` — whether the skill reduced tool calls (positive) or added unnecessary calls (negative)
   - `avg_quality_score` — average quality score from LLM judge (1-10 scale) _(LLM judge enhancement)_
   - `avg_tone_score` — average tone score from LLM judge (1-10 scale) _(LLM judge enhancement)_
   - `avg_helpfulness_score` — average helpfulness score from LLM judge (1-10 scale) _(LLM judge enhancement)_
   - `avg_adherence_score` — average instruction adherence score from LLM judge (1-10 scale) _(LLM judge enhancement)_
   - `judge_coverage` — % of evaluations with LLM judge data
4. **Presents a summary** to your terminal showing:
   - Top effective skills (candidates for pinning)
   - Low-effective skills (candidates for archiving)
   - Skills with insufficient data (need more evaluations)
5. **Optionally auto-actions** via the curator:
   - Pin skills with `effective_rate >= 80%` and `avg_quality_score >= 7.0`
   - Archive skills with `effective_rate < 30%` AND `use_count >= 3`

> **Pitfall**: Skill names are NOT automatically included in trace JSON records. This skill infers skill names from evaluation patterns:
>
> - If you repeatedly evaluate the same task with the same skill loaded, track which skill was active by checking `hermes skills list` before each run, or include the skill name in your task prompts (e.g.: `"Evaluate my-governance-skill: Research Python web frameworks..."`)
> - Without explicit skill-name tracking, this skill groups all evaluations together under a generic label — you lose the per-skill effectiveness breakdown
> - **Always include the skill name in your task prompt** when you want meaningful effectiveness data per-skill, e.g.: `"Evaluate my-governance-skill: Research Python web frameworks with security focus and compare them"`

> **Why**: The `run-the-trace` trace JSON NOW includes a `skill_name` field when the skill name is included in the task prompt (e.g., `Evaluate my-governance-skill: ...`). This enables per-skill effectiveness metrics. If you don't provide the skill name in your prompt, this skill will show aggregate metrics only (no per-skill breakdown). Making this a standing practice (include skill name in prompt) is the most impactful improvement you can make.

## Trace JSON format (from run-the-trace)

Each execution creates a JSON file like:

```json
{
  "timestamp": "2026-10-20T14:30:00Z",
  "task": "Research Python web frameworks with security focus and compare them",
  "skill_name": "my-governance-skill",
  "without_skill": {
    "output": "[WITHOUT_SKILL] Research Python web frameworks with security focus and compare them",
    "execution_time_seconds": 4.2,
    "tool_calls": ["terminal"],
    "success": true
  },
  "with_skill": {
    "output": "[WITH_SKILL] Research Python web frameworks with security focus and compare them",
    "execution_time_seconds": 8.5,
    "tool_calls": ["terminal", "web_search"],
    "success": true
  },
  "difference": "with_skill was 2.0x slower but included web_search; baseline run first to mitigate carryover effects",
  "skill_effective": true,
  "with_skill_better": "Y"
}
```

> **Note about skill names**: The `run-the-trace` trace JSON NOW includes a `skill_name` field when the skill name is included in the task prompt (e.g., `Evaluate my-governance-skill: ...`). This skill tracks effectiveness per-skill-name based on the evaluation sequence. Skill names are associated with evaluations by the user providing contextual identifiers when prompted, or by tracking which skill was active during each `run-the-trace` invocation. For curator integration, skill names are typically the names you've loaded (visible via `hermes skills list`) during the evaluation runs.

## LLM-as-a-Judge Enhancement

This enhancement adds qualitative evaluation of skill performance using an LLM as a judge, complementing the existing quantitative `effective_rate` metric.

The `skill-evaluator` can now evaluate skill performance across four dimensions using an LLM judge:

- **Quality**: Overall output quality (1-10 scale)
- **Tone**: Appropriateness of tone for the task (1-10 scale)
- **Helpfulness**: How well the output helps complete the task (1-10 scale)
- **Instruction Adherence**: How well the output follows task instructions (1-10 scale)

## How It Works

1. **Trace records** must include `skill_name` field (added in `run-the-trace` v1.1+)
2. **skill-evaluator** reads all `run-the-trace` JSON files from `~/.hermes/traces/`
3. For traces with `skill_name`, the skill uses an LLM judge to compare `without_skill` vs `with_skill` outputs
4. Scores are aggregated per skill and presented in the effectiveness summary

## Judge Prompt Templates

The skill sends the following prompts to the LLM judge for each evaluation:

```
### Quality
Rate the quality of the output on a scale of 1-10, where:
- 10 = Perfect, production-ready output with no issues
- 7-9 = High quality, minor improvements needed
- 4-6 = Functional but needs work
- 1-3 = Unusable or major issues present

### Tone
Rate the tone appropriateness on a scale of 1-10, where:
- 10 = Perfectly matched to the task context and audience
- 7-9 = Appropriate with minor mismatches
- 4-6 = Partially appropriate, significant mismatches
- 1-3 = Inappropriate or wrong tone

### Helpfulness
Rate how helpful the output is for completing the task on a scale of 1-10, where:
- 10 = Output fully resolves the task, no further action needed
- 7-9 = Output resolves most of the task, minor gaps
- 4-6 = Output provides partial help, significant gaps remain
- 1-3 = Output provides little to no help

### Instruction Adherence
Rate how well the output follows the task instructions on a scale of 1-10, where:
- 10 = Output perfectly follows all instructions, no deviations
- 7-9 = Output follows most instructions, minor deviations
- 4-6 = Output follows some instructions, significant deviations
- 1-3 = Output ignores most instructions
```

## LLM Configuration

The judge model is configured via:

- `hermes config set model <model_name>` - sets the default model for the session
- `HERMES_JUDGE_MODEL` environment variable - overrides the default
- If not configured, defaults to the session's default model

Example: `hermes config set model nemotron-3.5-lightning:free`

## Computed Metrics

When LLM judge data is available, `skill-evaluator` computes these additional metrics:

| Metric                  | Description                                                     |
| ----------------------- | --------------------------------------------------------------- |
| `effective_rate`        | % of evaluations where `skill_effective: true` (quantitative)   |
| `avg_quality_score`     | Average quality score from LLM judge (1-10 scale)               |
| `avg_tone_score`        | Average tone score from LLM judge (1-10 scale)                  |
| `avg_helpfulness_score` | Average helpfulness score from LLM judge (1-10 scale)           |
| `avg_adherence_score`   | Average instruction adherence score from LLM judge (1-10 scale) |
| `judge_coverage`        | % of evaluations with LLM judge data                            |

## Backwards Compatibility

- Traces **without** `skill_name` field: `skill-evaluator` shows aggregate metrics only (no per-skill breakdown, no judge scores)
- Traces **without** judge data: `judge_coverage` will be < 100%, and average scores computed from available data only
- New traces **with** `skill_name` and judge data: full per-skill qualitative + quantitative metrics

## Usage Example

```bash
# Ensure skill name is included in your run-the-trace prompts:
/skill run-the-trace
#? Task: Evaluate my-governance-skill: Research Python web frameworks with security focus and compare them

# Then analyze:
hermes --skills skill-evaluator
# Shows: effective_rate + quality/tone/helpfulness/adherence scores + judge_coverage

# Auto-actions consider both quantitative and qualitative data:
hermes curator pin compliance-classifier  # High effectiveness + high quality scores
hermes curator archive rate-limiter       # Low effectiveness + low quality scores
```
